# 构建与性能排查记录

2026-11-17 对当前部署链及应用代码的检查，基线为 `c653a8a`。下面是本地可复现实测；Zeabur 只提供了部署状态，尚未获得其各阶段构建日志，因此不把本地数字当作平台耗时。

## 发现与修正

| 位置 | 实际问题 | 本次处理 |
| --- | --- | --- |
| Firefox 自动打包 | 普通网页修改也触发 ZIP 提交，随后 Zeabur 又开始部署；两次历史扩展 ZIP 内容相同，却有 417 项时间戳不同 | 仅扩展或提交材料变化自动打包；固定归档顺序、时间与权限；过期任务不覆盖主分支 |
| Docker 构建输入 | 原生客户端、扩展归档及其重复网页副本、离线编写材料进入网页镜像 | 排除无关目录，保留根目录 Python、模板、网页资源及生成后的离线包 |
| 图标生成 | 普通业务文件变化后重复生成全部平台图标 | 图标独立缓存，只生成网页版本；62 个网页文件与原输出逐字节一致 |
| 模型准备 | 准备命令已做最终完整校验，Docker 又立即执行一次 `--verify-only` | 去除第二次扫描，保留准备命令内部的完整校验和独立检查命令 |
| 图谱节点选择 | 每点一个节点，为更新历史数量重新复制和解析全部对话 | 纯节点选择复用数量；数据刷新、切换范围或打开历史时重新汇总 |
| 浏览器回归 | 新对话依赖字体自然高度，新概念有 44px 最小高度，CI 字体下出现 43 / 44px 差异 | 两者统一 44px 最小高度；字号、内边距和测试断言保留 |

使用实际 Docker `COPY` 并导出文件树比较同一份工作区：应用输入从 **97,919,535 字节 / 1483 个文件**降到 **25,297,744 字节 / 578 个文件**，减少约 **74.2%**。这是应用文件量，不包含安装依赖、模型或整个镜像的大小。

## 本地测量

| 操作 | 结果 |
| --- | --- |
| 默认应用导入 | 约 0.83 秒；阻止网络连接时仍成功，未加载 Paddle / ONNX Runtime |
| 300 个文件、约 22MB 的源码指纹 | 41～59 毫秒 |
| 137 个根目录 Python 文件编译 | 约 0.49 秒 |
| 旧全平台图标生成 | 约 6～8 秒 |
| 有效模型缓存准备 | 约 2.55 秒，无下载、无转换 |
| 紧接着的重复模型校验 | 约 1.19 秒，额外读取约 195MB |
| 5000 条消息、约 7.9MB 的图谱选择 | 旧路径汇总约 181～293 毫秒；修正后的详情更新约 0.1～1.2 毫秒 |

冷构建仍需要安装大型 Python 依赖、下载约 156 MiB 官方模型并生成约 30 MiB 的 ONNX 文件。缓存被清理或更换构建节点会影响这些成本，尚不能据此确定上次约 14 分钟部署中哪一阶段占比最大。

`app.py` 约 5700 行、`static/script.js` 约 23000 行，职责集中确实增加维护负担。后续模块化应优先沿图谱、对话、账号等边界拆分，并保持现有交互回归；本次先消除了已测到的重复工作。

验证入口为 `test-web-build.yml`、`validate-ocr-model-cache.yml`、Firefox 打包工作流及图谱浏览器回归。首次更新打包脚本会发布一次规范化归档，之后普通网页改动不会再触发扩展打包提交。
