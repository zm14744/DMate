# 全链路诊断与修复依据（冻结诊断基线）

## 结论与证据边界

本轮先冻结开发稿，再定位故障、查阅对应资料、确定架构修改，最后实施。这里记录的是修复前诊断，不是上线报告或识别成功证明。

基线同时保留两个最新开发分支，合并提交为 `5e6a9e6`。诊断在此提交之上的工作稿执行，每个批次另外记录实际源码 SHA-256，不能只用 Git 提交号描述未提交的代码。原图、人工参考和逐图原始响应保存在私有验收包，未写入公共仓库；浏览器截图仅用于本地人工检查，不包含在交付压缩包中。

当前系统的根本问题是证据对象之间的边界不够明确：版面框被当成数学子图，圆形文字可能被当成节点外边界，像素路径可能被当成独立边实例，模型自报完整可能被当成完整验收，进程正常返回可能被当成识别成功。这些错误会相互放大，单独换提示词或增加图像增强不能解决。

### 已执行的冻结实验

| 实验 | 观测结果 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 53 张原图统一解码与墨迹分层 | 全部执行完成、没有空墨迹输出 | 透明底/颜色/方向处理能运行 | 颜色与弱墨迹语义全部正确 |
| 本地版面与文字全量 v2 | 版面 53/53 执行完成；文字 52/53；1 张文字 worker 超内存 | 存在可复现的资源故障 | 52 张文字或 53 张版面内容正确 |
| 独立故障定位探针 | 首次原图文字检测进入后 RSS 超过 1600 MiB，识别器和增强第二遍尚未进入 | 超限发生在第一遍检测路径 | 尚不能细分到具体算子、预处理或后处理内存 |
| 给定正确节点的候选隔离 v2 | 85 个面板、544 个节点；765 条参考边中，支持候选的端点/重数匹配容量为 717 | 在理想节点条件下，候选仍存在缺失 | 717 条真实边正确；方向、路径、属性均未由此认证 |
| 仅取参考已确认的面板 | 83 面板、738 条边，支持候选容量为 701 | 参考不确定性不能解释全部候选缺失 | 端到端召回率或整图通过率 |
| 合成前端契约 | 7 个桌面/移动场景，67 项检查；远端 OCR 调用 0 | 结构、状态、转义能展示 | 原图视觉模型或实际识别正确 |
| 原始透明 PNG 预览 | 深浅主题的浏览器底色与后端白底合成不同 | 存在展示与识别输入不一致 | 深色主题完全没有边；实际是低对比和不同底色 |
| Flask `/ocr` → `/ready` 故障注入 | 文字返回 memory_limit 后，仍出现 ready 和公式降级文案 | 状态传播错误已复现 | 生产环境已经发生相同调用 |
| Qwen/DeepSeek 全链路 | 0 次真实远端调用，凭据缺失 | 当前不能出具完整验收 | 不能用 mock 或本地执行结果替代 |

本地 OCR v2 总用时 904.652 秒，106 个阶段均观测到 RSS，5 个相关生产文件起止指纹一致。测量使用两 CPU 亲和性，宿主内核配额仍是 8 CPU/8 GiB，应用预算为 4 GiB，Python 为 3.12；目标部署是 Python 3.10、实际 2 CPU/4 GiB 容器，二者不能等同。

## 诊断清单

证据等级：**实测**表示冻结输入已复现；**源码**表示可由控制流或协议直接证明；**待真测**表示不能在缺失远端凭据时下结论。

| ID | 根因与影响 | 证据 | 修复设计与验收 |
| --- | --- | --- | --- |
| D01 | Paddle 检测默认 `64/min/4000` 与当前图像尺寸组合，仍接近全幅卷积；大照片第一遍检测超 RSS | 实测 + 安装包源码 | 显式限制检测最长边；文字识别仍使用原图裁片；记录 det/rec/pass，重新全量观察 RSS |
| D02 | 本地布局和文字共用最长边 2200 的已缩图副本，小字细节提前丢失 | 源码 | 布局副本与文字原图分离；检测下采样不等于识别裁片下采样；输出坐标需保留原图映射 |
| D03 | 版面模型输出的 figure 不是数学子图：可合并多个例图、漏孤立点；2 张无任何区域、另1张仅文字区域 | 实测 | 版面只作提示；第二轮须重新确认全页面板，包括孤立点和外弧；不得以区域数等同图数 |
| D04 | 当前第二轮能改节点，但面板 ID、数量、框不可修正；第一轮漏/合并图后没有合法纠错通道 | 源码 | 增加显式面板修订协议，追踪旧节点和候选归属，支持新增/删除/拆分/合并/扩大框，不增加视觉调用 |
| D05 | 节点半径只用固定圆周覆盖门槛；略椭圆/缺口外圈未过阈值，退回数字内部小圆 | 实测 | 测量带置信度的轮廓、半轴和出线端口；外圈与内部字形分离；不能只继续扩大半径上限 |
| D06 | 虚线判定用所有白缝 max/min；端点截断的短白缝改变后使更完整候选被拒绝 | 实测 | 排除端部截断间隔，对完整 dash/gap 统计稳健分布，保留明确的不确定状态；验证实线误接不会增加 |
| D07 | 空心箭头两条外轮廓、粗线偏移路线与真实平行边缺少可靠实例层 | 实测 + 源码 | 分离线段/路线/连接实例；保留独立端口、头尾、白缝、原图支持；相同端点绝不直接去重 |
| D08 | 局部交叉转向 veto 会混淆节点出线扇区与真正交叉，路径在交叉处也可能串线 | 实测 | 候选局部切线、节点轮廓距离与端口共同判断；不能全局关闭交叉检查或按图名补边 |
| D09 | 用无序端点计数判多重图，会把 A→B 与 B→A 各一条误算成同向平行边 | 源码 | 有向边按有序端点、无向边按无序端点计数；独立边 ID 永远保留 |
| D10 | 原图中浅色正面线、透印、阴影、背景装饰均可能有真实像素，像素存在不足以证明数学边 | 实测 + 待真测 | 强弱证据及语义归属分离；辅助增强只提候选，最终用原图复核；不把所有弱线删掉 |
| D11 | 方向、权值、边名依赖视觉模型；reads 与 edges 一致仅是同一输出的自洽 | 待真测 | 逐实例保存视觉与像素来源；严格比对有属性的多重边，不能把 coverage=true 当正确性 |
| D12 | 第一轮题干直接替代 Paddle 文本，缺少局部证据冲突检查；校正器又故意保护数字 | 源码 | 保留两种转录和定位证据；第二轮处理关键字符冲突；数字、变量、运算符不能由普通润色静默改动 |
| D13 | 单模块两次预算并非 HTTP 请求级共同上限；异常后旧链回退缺乏统一阻断 | 源码 | 从 `/ocr` 路由进入新链后失败关闭，不再发起旧链；网络 ledger 与 provider metrics 对账 |
| D14 | 完整验收只要求出现 Qwen 调用，现有测试一调用也能获证；缺发送记录与模型记录对应 | 源码 | evidence-two-pass 的完整证书要求恰好两次成功视觉发送并一一对应；失败可提前停止但不可 complete |
| D15 | 文字 worker 失败仍返回普通字典；API 将 warning 一律归成公式降级，并写 ready=true | 实测 | 服务健康、任务成功、识别完整分开；返回明确阶段状态，界面准确展示失败/部分成功 |
| D16 | 浏览器直接展示透明原图，后端使用白底合成 | 实测 | 原图预览使用白底，与后端 canonical RGB 一致；原始上传字节不改写 |
| D17 | token、图数、候选数有硬限但最大容量未真测；过长输出可能不闭合 | 源码 + 待真测 | 根据实际清单调整输出预算、显式报告容量和截断；不可隐藏截断或补第三次调用 |
| D18 | 人工参考有2张结构/属性细节不清，另1张题干被裁切 | 人工原图复核 | 保留不确定项；当前51张结构参考可用、50张全内容可认证；需更清晰原图/原始题干才能认证另外3张 |
| D19 | 本地依赖/内核条件与目标容器不完全相同 | 实测 + 源码 | 使用仓库 Dockerfile 在真实2 CPU/4 GiB限制下执行资源门禁；开发机测试不代替生产配置门禁 |
| D20 | DeepSeek封装返回content，校正模块却读reply，可能将空解析报告为ok | 源码 | 读取实际content并严格校验edits结构；合法零改动与无效响应区分；拒绝数学内容润色 |
| D21 | 仅保护ASCII/数字或有限中文词表不够：中文数词、逻辑词、颜色、指令、数学字母、组合向量/上划线和组合编辑均可能改写题意 | 独立反例实测 | 按完整内容签名检查单项与组合后全文，仅允许明确等义字形/空白；实质改字交给原图复核 |
| D22 | 只核对graph_id而不核空间关系，可能把图外题干排成graph_label后仍complete | 独立反例实测 | 图内标签排除必须有定位框与最终面板的空间支持；缺定位或矛盾不得认证 |
| D23 | 空心箭头轮廓凭证未绑定模型返回路径，同候选ID/端点可借凭证支持空白绕路 | 修复阶段独立反例实测 | 原图边界凭证同时约束中轴、端口、投影覆盖及顺序；允许白色中轴，但禁止借用同端点其他实例；中止旧批次并重新冻结全量运行 |

候选隔离 v1 到 v2 的支持容量由 566 增至 717，但未被端点/重数匹配占用的支持候选由 65 增至 84。后一项不是精确假阳性数量，因为端点匹配没有判定几何实例；它足以说明“候选更多”不能自动解释为“识别更准确”。v2 有三处候选层回归，必须保留失败记录并逐一分析，不能只报告总体提升。

## 五个历史问题与架构落点

| 问题 | 已有有效基础 | 仍要解决的根因 | 完成定义 |
| --- | --- | --- | --- |
| 颜色 | RGB、色差与亮度墨迹、白底 alpha 合成 | 浏览器背景不同；颜色不能直接等于边实例身份 | 彩色节点/边逐项对应正确，透明图预览与识别输入一致 |
| 透印 | 强弱墨迹分层、原图保留 | 浅正面与背面可能同样有像素 | 每条保留/排除均由原图语义和归属支持，不删真实浅线 |
| 模糊 | 有限锐化作辅助、原图裁剪 | 预先缩图损失细节；圆环/箭头/数字不稳定 | 未改变真实拓扑；模糊到不可读项明确待确认 |
| 分图 | 全页与全部子图复核 | 首轮面板清单不可修订，layout不等于数学图 | 每个数学图含全部外弧与孤立点，多分量不误拆，多例图不误合 |
| 阴影 | 低频背景归一化、原图支持核对 | 模型内存和纸外背景干扰 | 原照片单次执行、全部目标结构正确，桌面/封面不计入图 |

## 资料选择与不采用的假设

详细来源及旧18项阅读见 [研究综述](GRAPH_RECOGNITION_RESEARCH_20261026.md)，本轮补充见 [拓扑研究补充](GRAPH_TOPOLOGY_RESEARCH_ADDENDUM_20261026.md)。参考文献应解决已定位的问题，不按论文数量决定实现。

1. [Optical Graph Recognition（2013）](https://jgaa.info/index.php/jgaa/article/view/paper303) 与 [Optical Graph Edge Recognition（2018）](https://www.scitepress.org/Papers/2018/65504/) 支持分离节点几何、线段续接和拓扑重建。采用端点几何、方向连续性、实例追踪；其评测条件不能直接当作本系统照片性能。
2. [Arrow R-CNN（2021）](https://link.springer.com/article/10.1007/s10032-020-00361-1) 使用箭头头尾定位连接节点，适合借鉴连接实例。其4.2节会消除同方向、同端点的重复候选，依赖“每方向最多一边”假设；DMate 的数学多重图不能照搬此规则。论文 V100 指标也不是2核CPU证据。
3. [PolyVector Fields（2018/2019）](https://arxiv.org/abs/1801.01922) 提供交叉处多方向场和拓扑重建思路；其旧 C++依赖与耗时不适合作为本次默认链直接引入。局部方向一致性可借鉴，不安装整套模型/优化器。
4. [TopoAgent（2026，预印本）](https://arxiv.org/html/2608.28701v1) 的节点清单、逐节点关系清点和局部证据有参考价值。但原文逐节点推理产生多个子问题；本系统两次请求内的批量逐节点清点不是其完整复现。附录C.3自动补逆向关系、强制单连通并移除断开部分，与数学无向边、孤立点和多分量图冲突，明确不采用。
5. [PaddleOCR 官方参数](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html) 与实际安装的3.7.0/3.7.2代码共同决定内存修复。只限制 detector 的尺寸，保留 recognizer 对原图裁片的访问；不能凭文档某个默认值推断实际初始化后的参数。
6. [PaddleX 版面分析](https://paddlepaddle.github.io/PaddleX/latest/en/module_usage/tutorials/ocr_modules/layout_analysis.html) 描述的是页面元素类别、轮廓和阅读顺序；本系统将其作为候选。子图分割、孤立点归属仍需单独建模。
7. 阴影/透印/文档恢复研究支持分离低频背景与笔画，但不构成恢复丢失事实的证据。采用轻量图像辅助，不部署未经2核4GiB验证的重型恢复网络，不以美观作为文字或拓扑正确性指标。

这些是结合原文和本项目约束作出的工程取舍，不是论文对本项目的性能保证。

## 修复与验收顺序

1. 固定规范图像、内存阶段记录与准确状态；修复资源故障，建立可运行的基础。
2. 修复节点轮廓与虚线回归，保留候选实例身份；重新执行候选隔离，报告回归与额外候选。
3. 实现可修订的第二轮面板清单和题干冲突协议；全程保持最多两次 Qwen、无自动重试。
4. 完善应用级失败关闭、前端白底与严格验收 ledger；进行针对根因的合成/故障注入测试。
5. 冻结最终源码，用同一版本依次运行全部53原图，保留所有失败和不确定项。只有真实模型、原图结果、独立参考、前端关联和资源门禁全部满足，才能报告整图单遍通过。

缺少真实凭据与3张参考不完整是当前验收阻塞，不影响先完成上述已定位的代码修复。任何“全通过”结论必须在这些阻塞解除后由新一次完整冻结运行产生。
